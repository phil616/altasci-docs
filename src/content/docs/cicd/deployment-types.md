## 先确定交付对象

编写流水线前，先确认项目最终产出什么、由谁运行，以及配置在构建时还是运行时生效。本文整理 AltasCI 常见的三种交付形式；一个项目可以组合使用多种形式。

| 形式 | 交付对象 | 常见运行方式 |
| --- | --- | --- |
| 单体 Web 服务 | 容器镜像或可执行程序 | Docker 或 systemd 管理的 Linux 服务 |
| 前后端分别部署 | 前端静态文件与后端服务 | 前端交付到静态托管，后端部署到 API 服务主机 |
| CLI 交付 | 部署工具接收的文件、镜像或资源描述 | CI 提供运行环境，由平台 CLI 完成上传与发布 |

文中的 `example.com` 域名与应用名称仅作示例，不是实际部署入口。

## 单体 Web 服务

当一个对外入口同时提供页面和 API 时，可以将其作为同一个部署单元处理。例如：

```text
app.example.com/        → 页面
app.example.com/api/    → API
```

即使代码按前端和后端组织，只要对外入口与发布单元合并，也可以采用这种交付方式。

使用 Docker 时，流水线构建并推送镜像，由部署阶段加载配置后启动容器。使用 systemd 时，部署阶段交付程序和服务配置；修改 unit 文件后需要重新加载 unit，再按项目流程重启服务。

发布后应能确认程序或容器启动成功、配置文件已正确加载，并且预期入口可访问。运行时变量的处理见[部署凭据与应用配置](/docs/cicd/credentials/)。

## 前后端分别部署

前端页面与后端 API 使用不同域名时，通常需要两条交付路径：

```text
app.example.com      → 静态托管或 CDN
api.example.com      → 后端服务
```

前端通过 CI 构建出静态文件并上传；后端可以构建为容器镜像，再交付给部署主机。两部分可以位于同一仓库，也可以独立维护。

### 浏览器访问配置

| 项目 | 需要确认的内容 |
| --- | --- |
| API 基础地址 | 前端构建或运行配置指向正确的 API 环境 |
| CORS | 后端允许预期前端来源，并按实际请求配置方法、请求头与凭据策略 |
| CSP | 前端页面的 `connect-src` 等策略允许连接所需 API |
| Referer 相关规则 | 如现有网关检查该请求头，需适配实际请求；它可能缺失，不能单独作为身份认证依据 |

CORS 管理浏览器跨源访问，不能代替服务端身份认证。相关行为可参考 [MDN 的 CORS 说明](https://developer.mozilla.org/zh-CN/docs/Web/HTTP/Guides/CORS)与 [CSP `connect-src` 说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/connect-src)。

## 使用 CLI 交付

在 CLI 交付中，CI 平台负责提供运行环境、构建产物和授权变量，部署工具负责将产物交给目标平台。通过 EdgeOne CLI 上传静态文件就属于这种形式。

接入时应确认 CLI 版本、认证变量、目标项目、输出目录以及命令退出状态。将 CLI 版本固定在项目依赖或受控镜像中，避免每次发布临时使用不同版本。

前端构建变量会进入浏览器可下载的内容，只能放公开配置。API Token、服务端口令和私钥应由 CI 或运行环境注入，不能通过前端变量发布。

## 组合发布与变更范围

同一仓库可以将前端交给 CLI 部署，将后端构建为 Docker 镜像。配置路径过滤时，除业务目录外，也要考虑共享代码、依赖清单、锁文件和流水线配置本身的变化，避免漏掉需要重新构建的变更。

两部分分别构建不代表可以任意顺序发布。涉及 API 兼容性变化时，应先确定版本兼容与发布顺序，再编排阶段。CNB 配置示例见 [CNB 流水线配置](/docs/cicd/cnb-pipelines/)。
