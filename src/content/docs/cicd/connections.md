## 先确认连接通道

主机部署需要一条已授权的连接通道。AltasCI 的主机交付使用直接 SSH，或通过受控代理接入 SSH。选择哪种方式取决于项目的网络和访问配置，不能根据 NodeID 猜测 IP、端口或可用权限。

本文提供连接方式说明，不公布真实主机地址、密钥仓库位置或访问策略。

## 直接 SSH

目标主机可以从构建环境访问时，部署阶段通过 SSH 执行发布脚本。部署约定使用预先配置的专用部署用户和私钥认证，不使用 SSH 密码登录。

| 参数 | 作用 | 示例变量名 |
| --- | --- | --- |
| 主机 IP 或访问域名 | SSH 连接目标 | `DEPLOY_HOST` |
| SSH 端口 | 服务端监听端口 | `DEPLOY_PORT` |
| 登录用户名 | 执行部署任务的身份 | `DEPLOY_USER` |
| 登录私钥 | 客户端认证材料 | `DEPLOY_SSH_KEY` |
| 已核验的主机密钥信息 | 核对服务器身份 | 由受控 `known_hosts` 配置提供 |

示例变量名仅说明参数用途，不是平台内置变量，也不意味着目标项目已配置这些值。“SSH 四元组”指主机、端口、用户和私钥；主机身份核验还需要独立的配置。

### 参数从哪里来

在 CNB 流程中，连接材料由受控密钥配置通过 `imports` 等机制提供，不写入业务仓库。引用文件的授权范围需要与调用仓库、分支和事件匹配；具体机制见 [CNB 文件引用文档](https://docs.cnb.cool/zh/build/file-reference.html)。

如果通过 SSH 插件执行任务，应按所选插件的文档设置主机、用户名、私钥、端口和超时，并确认主机指纹核验能力。不能将一个插件的 `settings` 参数直接套到另一插件，也不应通过关闭主机校验来掩盖配置问题。

## 通过受控代理接入

部分部署环境不直接向构建节点开放 SSH 端口，而是通过代理通道提供访问。使用 `cloudflared` 接入时，先建立符合访问策略的通道，再执行 SSH 认证与部署。

使用这种方式时，应分别确认代理认证和 SSH 认证。交互式浏览器登录可用于人员访问，但不能未经验证就作为无人值守流水线的认证方案；自动化任务需要使用接入环境明确支持的方式。

`cloudflared` 的具体命令和 SSH `ProxyCommand` 取决于配置方式，请参考 [Cloudflare 的客户端 SSH 接入文档](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/use-cases/ssh/ssh-cloudflared-authentication/)。不使用代理方案的项目无需增加这一步。

## 连通后的部署步骤

1. 核对当前连接的目标主机和部署用户。
2. 使用独立部署凭据验证制品仓库访问，确认所需版本可以获取。
3. 按 AppID 同步[应用配置](/docs/cicd/credentials/)，确认材料准备成功。
4. 按项目发布方式更新容器或服务，再检查启动、访问和版本。

连接成功只说明通道和认证可用。制品仓库授权、配置材料读取和服务管理权限仍需分别确认；排查时应保留阶段与错误现象，避免将私钥、Token 或完整环境文件写入日志。
