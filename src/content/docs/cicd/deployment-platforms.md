## 部署目标是什么

在本板块介绍的主机部署流程中，CD 目标是承载应用的 Linux 主机。这里介绍的 AltasCI 主机环境以 Debian 系发行版为主，服务通过 Docker 或 systemd 等方式管理。

静态站点托管、CDN 项目与主机部署是不同目标类型。选择交付方式时，先确认应用是否真的需要主机、常驻进程和运行时配置，不必为静态文件额外引入服务器部署步骤。

## NodeID 与连接地址

NodeID 是部署目标的管理标识，用于在发布流程和运维记录中指向同一台目标主机。命名方式包含供应商代码、序号，或供应商代码、地域与序号的组合。

```text
<供应商代码>-<序号>
<供应商代码>-<地域>-<序号>
```

这些是格式说明，不是可连接的主机地址。供应商代码和序号需要结合完整 NodeID 使用；不能仅凭一个序号判断主机身份。

| 信息 | 作用 | 是否可互相代替 |
| --- | --- | --- |
| NodeID | 运维与发布记录中的目标标识 | 不能代替 SSH 连接参数 |
| hostname | 操作系统或网络配置中的主机名称 | 不保证与 NodeID 一致 |
| IP 或访问域名 | 网络连接目标 | 可能随网络或代理配置变化 |
| SSH 主机密钥指纹 | 核对所连接服务器的身份 | 需要通过可信配置提供，不能从命名推导 |

实际主机清单、采购关系、访问域名与连接参数由项目接入配置管理，不在公开文档中列出。

## AppID 与运行对象

AppID 用于标识应用，关联凭据材料、同步命令和运行对象。它与 NodeID 的职责不同：前者回答“部署哪个应用”，后者回答“部署到哪台主机”。

例如，本文使用的示例 AppID `example-api` 可以关联 `/run/baoctl/example-api.env`。容器或服务名称也应有清晰对应关系，避免更新服务时读取了另一个应用的配置。

AppID 应使用适合目录与工具处理的稳定名称，避免斜杠和反斜杠。环境分类通过凭据配置表达，不应临时改变 AppID 来绕过既有约定。详细路径见[部署凭据与应用配置](/docs/cicd/credentials/)。

## 发布前确认

1. 确认目标环境、完整 NodeID、应用 AppID 与制品版本。
2. 确认运行方式、应用监听端口，以及现有反向代理的转发关系。
3. 确认专用部署用户已具备执行所需操作的权限。
4. 确认应用配置已准备好，且当前制品与配置版本兼容。
5. 确认发布后如何检查启动、访问与版本，以及失败时使用哪个制品恢复。

完成确认后，发布记录应能关联到应用、主机、制品和执行结果。不要把“SSH 已连通”或“部署命令返回成功”单独当作业务可用的证明。
